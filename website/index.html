Pre-alpha

afterlit is being built to help your Bluetooth gadgets keep working after their maker drops support.

Pre-alpha. The source is private, there is no public download yet, and testing on real devices is still pending.

A second life for your smart devices. afterlit first checks whether a free project already supports your device. If none does, it helps you investigate local Bluetooth control.

Runs on your computer · Asks before every device write

What you can do today

If your device's app or cloud service has stopped working, afterlit cannot help you directly yet. These three steps are worth doing in the meantime.

  1. 01 Search for a free project.Search the web for your device's name, as it appears in Bluetooth settings or on the box, together with "Home Assistant" (free home-automation software) or "open source". Many Bluetooth gadgets already have free, local software from other projects. Check that the project names your exact model, and follow its own instructions. afterlit has not tested these projects. Not sure it is Bluetooth?
  2. 02 Keep the vendor app and the pairing.Leave the vendor app installed and the device paired with your phone. To investigate a device, a contributor records the Bluetooth messages between the vendor app and that device, so the app is worth keeping even if its cloud features have stopped.
  3. 03 Check back later.There is nothing to download or sign up for yet. The status table further down this page lists what is available, what is pending and what is not built yet.

Useful hardware shouldn't expire with a server.

When no free project supports a device, afterlit gives contributors a way to work out its commands on their own computer. It asks before each write it sends to the device, and a change counts only when the device reports it back.

Is your device already supported?

This page has no lookup box. The device check (afterlit check) is part of afterlit's command-line tool (a program you run by typing commands in a terminal window), which is not public yet, so the examples below show how it answers.

Many Bluetooth gadgets already have free, local software from other projects. The device check looks for that first. You give it the name your device shows in Bluetooth settings, or its brand or model, and it compares that with a small built-in list on your computer, which its output calls the local catalog. A device counts as "freed" once free, local software can control it.

EXAMPLE OUTPUT · PRIVATE SOURCE ONLYNO RADIO USED
$ uv run afterlit check "ELK-BLEDOM 1A2B"
"ELK-BLEDOM 1A2B" is ELK-BLEDOM / duoCo Strip LED strips. Already supported by elkbledom (Home Assistant custom integration).
Install: HACS repository: https://github.com/dave-code-ruiz/elkbledom

$ uv run afterlit check "Desk Lamp"
"Desk Lamp" is not freed yet in the local catalog.
Contributors: afterlit scan, then afterlit capture android, then afterlit hunt.

$ uv run afterlit check "Smart Lock"
"Smart Lock" is out of scope.
afterlit will not touch it. The name contains a dangerous class (OTA/DFU, erase, reset, factory, lock or heat).

Above, in order: already supported, not freed yet, out of scope. Real output, shortened. The "Install:" line says where to get that independent project; it is not a step for installing afterlit. HACS is Home Assistant's community add-on store. capture android records from an Android phone running the vendor app.

  • Already supportedA free project lists this device family. afterlit names it, but does not run or test it.
  • Not freed yetNothing on the built-in list matches. A project may still exist elsewhere, so search as in step 01. If you own the device and want to help, see the contributor path.
  • Out of scopeafterlit refuses risky names and device families, such as lock, heat, reset or firmware update (OTA/DFU), even inside a longer word. It is cautious on purpose, so some harmless names are refused too. If yours is, go back to step 01 and search for a free project that names your exact model.
  • Local recipeOnly from a folder of recipes you supplied. There is no public recipe library.

Any match is a lead, not proof that your device will work. The wording shows how sure a match is:

"is"
a specific name pattern matched
"is likely"
look-alike devices share that pattern
"may be ... (unconfirmed match)"
only a brand or a loose hint matched

Is your computer ready for Bluetooth?

You do not need this yet. It is for when afterlit is public and you want to know whether your computer can talk to Bluetooth devices. If you only want to know what works today, skip to the current status.

The readiness check (afterlit doctor) looks at Python, the Bluetooth library afterlit uses and your operating system, and gives a one-line result for each, with a fix where needed. By default it writes no files and reads no credentials.

EXAMPLE OUTPUT · PRIVATE SOURCE ONLYNO RADIO USED
$ uv run afterlit doctor
OK AFL-D001 Python version: 3.14.0
OK AFL-D002 afterlit version: 0.1.0.dev0
OK AFL-D003 bleak installed: BLE extra is installed.
OK AFL-D004 bleak version: 3.0.2; afterlit requires bleak 3.x.
OK AFL-D005 OS support: macOS 27.0.1; requires 10.15 or later.
Not applicable AFL-D006 BlueZ client tool version: Linux only.
Skipped AFL-D007 macOS Bluetooth permission: Permission cannot be checked without prompting.
  Fix: Allow Bluetooth for the terminal app in System Settings > Privacy & Security > Bluetooth.
Not applicable AFL-D008 Linux user permissions: Linux only.
Skipped AFL-D009 Bluetooth adapter: Adapter not tested.
  Fix: Run with --radio to test the adapter.
No failures; review warnings and skipped checks before using Bluetooth.

Sample from one Mac; versions differ elsewhere. A clean report does not mean any particular device will work.

What the states mean and system requirements

Each line starts with a state word, then a short code naming the check (AFL-D001 to AFL-D009). Any "Check", "Problem" or "Skipped" line means your computer is not yet confirmed ready.

"OK"
the check passed
"Not applicable"
does not apply to your operating system
"Skipped"
not tested this time: Bluetooth permission cannot be checked without a prompt, and the adapter is tested only with --radio
"Check" (a warning)
worth reviewing before you use Bluetooth; the report's last line calls these warnings. None in this sample.
"Problem"
needs fixing first; Windows 10, for example, is reported as a problem. None in this sample.

Add --radio for a three second scan for nearby devices. It does not connect, pair, or read or write device data, but like any Bluetooth scan it may send standard scan requests, and your computer may ask for Bluetooth permission.

The readiness check expects Windows 11 (build 22000 or later), macOS 10.15 or later, or Linux with BlueZ 5.55 or later (BlueZ is Linux's Bluetooth system), and reports Windows 10 as a problem. These minimums come from the Bluetooth library afterlit uses (bleak), not from device testing.

The practice run

A rehearsal that touches no real device. You cannot run it yet. If you only want to know what works today, skip to the current status.

The practice run (afterlit demo) goes through the whole process on a simulated lamp, inside the command-line tool. It needs no Bluetooth radio, device, account or cloud service, and saves its files in a new folder each time.

EXAMPLE OUTPUT · PRIVATE SOURCE ONLYNO RADIO USED
$ uv sync
$ uv run afterlit demo
Practice run on a simulated lamp. No real device was touched and nothing left this computer.
3 of 3 controls confirmed by reading the device's state back.
Home Assistant / MCP / ESPHome outputs are developer drafts, not installable yet.
The key is temporary; the signature checks the receipt and activity log for changes, not who made them.

Output shortened. A finished run ends with exit code 0, meaning no errors. "The device's state" here is the simulated lamp's.

Terms and notes for developers

uv sync installs what afterlit needs. MCP lets AI assistants use tools; ESPHome is firmware for small Wi-Fi boards.

The run also lists the controls it learned, prints where its files are saved and shows the temporary key's fingerprint. Developers can still run the detailed afterlit hunt command. Its simulated strip carries a fixed 0xFF filler byte in the power frame, covered by a pre-declared allowance that the signed receipt records; a real device needs that allowance confirmed by hand.

For contributors: investigating a new device

This part is for people who own an unsupported device and want to help work out its commands. If that is not you, skip to the current status.

When the device check says "not freed yet" (nothing on its built-in list matches), a contributor who owns the device can investigate it. afterlit scan finds the device and checks the list again, afterlit capture records it (step 1) and afterlit hunt does steps 2 to 4. This path has not yet passed real-device testing (Gate 1).

01 Capture: observe first.

With afterlit capture, record the Bluetooth messages between the vendor app and a device you own, or use the built-in simulated capture.

02 Infer: find the pattern.

afterlit hunt turns the recording into a list of likely commands that you can review.

03 Verify: approve and check the result.

Each write needs your approval and starts from read-only. A command counts only when all its checks pass and the device reports the change back.

How the probe stays safe

The probe (the step that tests commands on a real device) starts read-only, and each write requires a new approval. It checks every fixed byte of each command (the parts that should never change), refuses dangerous command names and known firmware-update (OTA/DFU) targets, and never logs the Bluetooth characteristics (the named channels a device reads and writes through) that identify a device. Subscribing to the device's notifications (updates it sends on its own) needs approval too.

04 Save: keep the evidence.

afterlit saves a local driver, draft integrations, plain notes about the protocol and a signed record of what was tested.

What a run produces

The prototype emits starting points for local control and a record of what was actually tested. Generated integrations are drafts that need configuration and review.

  • Python driverLocal command encoding and state readback
  • Home Assistant, MCP & ESPHomeIntegration skeletons and drafts
  • PROTOCOL.mdHuman-readable protocol notes
  • Signed receiptIntegrity record for the run and action log

Questions about afterlit

Before you start

Is my gadget a Bluetooth device?

A rough guide: it probably is if it appears in your phone's Bluetooth settings, or if its vendor app asks you to turn on Bluetooth to set it up or control it. afterlit has no local-network (LAN) control, so a gadget that uses only Wi-Fi is outside it today. Step 01 still applies: search for a free project that names your exact model.

My device's app just stopped working. What now?

Start with What you can do today: search the web for your device's name together with "Home Assistant" or "open source", and keep the vendor app installed and the device paired. afterlit itself cannot help directly yet.

Can I use afterlit today, and how will I know when it is public?

Not yet. Current status shows which parts exist today, and it is where the public release will show. There is no signup or mailing list. Anyone can try the lamp preview on this page; it is only an illustration and connects to no device.

Will this work with any device?

No. The device check is the first step: it shows whether a free project already lists support for your device's family. A name match is a lead, not proof. For other devices, the real Bluetooth path has not yet passed Gate 1 (testing on a real device), every real-device write needs your approval, and generated integrations are drafts.

How it works

Do the device check or the readiness check touch my device?

Neither connects to, pairs with or writes to a device. The device check never uses Bluetooth; it compares the name you give it with a small built-in list. The readiness check uses Bluetooth only with --radio, for a three second scan that, like any Bluetooth scan, may send standard scan requests.

Does it flash firmware?

No. The current project does not flash firmware or bypass authentication, pairing, DRM, or licenses.

What does a receipt prove?

Its signature and hash chain (each log entry is linked to the one before, so a change shows) show whether recorded data changed after signing. Each run uses a one-off key by default; contributors can sign with their own key and verifiers can pin its fingerprint. A receipt does not prove that hardware was present or that an action was safe. Automated registry acceptance is not implemented.

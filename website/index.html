Why afterlit

Useful hardware shouldn't expire with a server.

afterlit uses local BLE captures to infer commands, asks for approval before each probe write, and checks the state reported by the device.

Steps

How afterlit works

01 / CAPTURE

Observe first.

Collect local BLE evidence from a device you own, or use the offline simulated capture.

02 / INFER

Find the pattern.

Turn capture bytes into a candidate command grammar that can be reviewed.

03 / APPROVE + VERIFY

Check the result.

Real-device writes require individual approval. A command counts only after all its checks pass and readback shows a driven-state change.

04 / EMIT

Keep the evidence.

Emit local driver and integration drafts, protocol notes, and a signed receipt for the observed result.

The probe starts read-only. Each write requires a new approval. The probe checks all frame bytes and refuses known OTA/DFU targets. Notification subscriptions need approval too.

FAQ

Questions about afterlit

Will this work with any device?

No. Each device has its own behavior, and the real-radio path still needs Gate 1 validation. A fingerprint match is only a lead, not proof of support.

Does it flash firmware?

No. The current project does not flash firmware or bypass authentication, pairing, DRM, or licenses.

What does a receipt prove?

Its signature and hash chain can show that recorded data has not changed since signing. CLI signing keys are ephemeral. A receipt does not establish who signed it, that hardware was present, or that an action was safe. Automated registry acceptance is not implemented.

Can I use it today?

Authorized source collaborators can run the offline demo and inspect the emitted files. Real hardware use is pre-alpha and requires per-write approval; generated integrations are drafts.
